# git-hygiene — 작업 이력을 증거로

작업 이력이 검토 대상이다. 커밋 하나가 "무엇을 왜 바꿨고 무엇으로 확인했나"를 말하면 사후 질문의 절반이 끝난다. OMC/OMX `git-master`의 원자 커밋 규율에 소유자의 브랜치 규칙을 더했다.

## 언제 쓰나
- 각 단계(`$execute`·`$debug`·`$cleanup`)가 끝났을 때
- 제출 직전
- 사용자가 커밋을 요청했을 때

## 절차
1. **저장소 스타일 감지**: `git log --oneline -20`으로 메시지 형식(conventional 여부, scope 사용, 언어)을 보고 따른다. 비어 있으면 `type(scope): 요지`.
2. **단위로 스테이징**: 한 커밋 = 한 논리 단위. 기능과 리팩터링, 테스트와 정리를 섞지 않는다. 비대화형 환경에서는 `git add -p` 대신 **경로를 지정해** `git add <파일…>`로 단위를 나눈다(한 파일에 두 단위가 섞였으면 그 파일은 한 커밋으로 두고 메시지에 둘 다 적는다). 완료 기준: 각 커밋의 diff를 한 문장으로 설명할 수 있다.
3. **커밋 전 스캔**(변경 파일 대상): 비밀값 패턴(token/key/password/Bearer, 알려진 접두), 제어문자, 임시 파일(`tmp/`, 로그), 디버그 출력, `TODO/FIXME`, skip된 테스트. 발견 시 커밋하지 않고 고친다. 테스트 픽스처의 더미 값(`TEST_KEY=dummy` 등)·정상 로그 문구는 **오탐**으로 분류하고 그 사유를 커밋 본문에 한 줄 적는다.
4. **메시지**: 제목 `type(scope): 요지`(50자 내외). 본문에 **왜**(한두 문장), **검증**(`명령` → 결과), **근거** `decision-log #n`. 축하·수식어 없이.
5. **브랜치 규칙**: 현재 브랜치에 커밋한다. 새 브랜치 생성·원격 push·force push·공유 커밋 amend는 사용자 승인이 있을 때만. `--no-verify` 금지.
6. **기록**: 커밋 해시·제목·연결 엔트리를 `$evidence-log`에 적는다.

## 규칙
- 커밋은 요청받았거나 과제가 커밋 제출을 요구할 때 한다. 임의로 하지 않는다.
- 테스트가 실패하는 상태로 커밋하지 않는다. 실패를 커밋해야 하면 제목에 `wip:`와 이유를 명시.
- 생성 파일·의존성 디렉터리·개인 설정은 `.gitignore`로 제외한다.
- 메시지의 명령·경로·오류 문구는 그대로 인용.

## 출력
- 커밋 목록(해시 · type · 요지 · 연결 엔트리)
- 스캔 결과(발견 0건 또는 처리 내역)
- 미커밋으로 남긴 변경과 이유
