# execute — 구현

목표: 합의된 의도를 동작하는 코드로 바꾸고, 동작한다는 증거를 남긴다.

## 절차
1. **크기 확인**: Trivial이면 리더가 직접 고친다. Scoped/Complex인데 계획이 없으면 `$plan`. 단, 사용자가 **이미 구현을 요청했고 범위·수용 기준이 명확**하면 `$plan`은 계획을 기록만 하고 바로 돌아온다(승인 왕복 없음). 완료 기준: 어떤 경로로 갈지 한 줄 기록.
2. **단위 분해**: 서로 파일이 겹치지 않는 독립 단위로 나눈다. 단위마다 담당 파일을 지정한다. 완료 기준: 단위 목록 + 파일 담당표.
3. **위임**: Trivial은 리더가 직접 한다. Scoped 이상은 역할·위험에 따라 위임한다. 독립 단위가 2개 이상이면 등록된 커스텀 에이전트 `cofa-worker`를 단위마다 spawn해 병렬로 돌리고, 단위가 하나여도 리더의 컨텍스트가 길거나 변경이 고위험이면 `cofa-worker`에 맡겨 작성 컨텍스트를 분리한다. 위임 프롬프트에 목표·범위(파일)·금지·완료 기준·보고 형식 다섯 가지를 모두 쓴다. spawn한 에이전트와 적용 모델을 기록한다.
4. **구현 규칙**: 기존 헬퍼·패턴 재사용, 최소 diff, 단일 사용 로직에 추상화 금지, 새 의존성 금지(명시 승인 시 예외), 인접 코드 리팩터링 금지.
5. **진행 중 검증**: 단위마다 타입체크·해당 테스트를 돌린다. 끝에서 한 번 돌리지 않는다.
6. **통합**: 리더가 모든 단위를 합치고 전체 빌드·테스트를 돌린다. 신선한 출력을 인용한다.
7. **넘기기**: `$review`(결함)와 `$verify`(증거)로 넘긴다. 작성한 컨텍스트가 스스로 승인하지 않는다.
8. **기록**: `$evidence-log`로 변경 파일·검증 명령·남은 것을 적는다. 구현 단위마다 `docs/submission-notes.md` 1절에 "변경 한 줄 · 파일 · 왜(사용자 요구 기준) · 검증 → 결과 · 엔트리" 한 행을 추가한다. 구현 중 사용자가 "그렇게 말고 이렇게"라고 방향을 바꿨으면 2절에도 한 행(`$submission-notes`).

## 막혔을 때
- 증거가 부족한데 결론을 내야 하거나 중대한 반례가 나오면 → 즉시 멈추고 `cofa-architect`에 증상·시도·가설을 넘긴다. 같은 시도는 원인 가설이 바뀌었을 때만 반복한다. 코드를 더 찍어보지 않는다.
- 범위가 계획보다 커지면 → 멈추고 사용자에게 범위 변경을 알린다.

## 완료 조건 — "구현 종료"와 "검증 통과"는 다르다
- 구현 종료: 미완 단위 0개, TODO 자리표시자·skip 테스트·스텁·디버그 출력 없음, 각 단위의 검증 명령과 결과가 기록됨
- 테스트 실패가 남아 있으면 "구현 종료"가 아니라 **미완**으로 보고하고 남은 실패 목록을 적는다. 실패를 "있는 그대로 보고"하는 것은 투명성이지 완료가 아니다
- 검증 통과는 `$verify`의 판정(필수 기준 전부 PASS)으로만 선언한다. 이 스킬은 선언하지 않는다

## 출력

- 구현 내용
- 실행한 검증 명령과 결과
- 남은 것 / 블로커
