# onboard — 저장소 지도 (읽기 전용)

OMX `analyze`의 증거 규율과 OMC `deepinit`·`architecture-survey`의 지도 만들기를 합쳤다. 코드를 고치기 전에 **무엇이 어디서 어떻게 도는지**를 증거로 적어두면 계획이 정확해지고, 사후 질문 "작동 원리를 설명하라"에 이 문서가 답이 된다.

## 언제 쓰나
- 과제 분류 직후, 계획 전(Scoped 이상은 필수)
- "왜 이렇게 동작하나", "어디서 이걸 처리하나" 같은 설명 질문
- 변경 영향 범위를 모를 때

## 언제 쓰지 않나
- 파일 1개의 자명한 수정(Trivial)
- 이미 `docs/onboard.md`가 있고 저장소가 바뀌지 않았을 때 → 읽고 넘어간다

## 절차
1. **질문·범위 고정**: 무엇을 알아야 계획을 쓸 수 있는지 한 줄. 완료 기준: 질문이 "답했는지 알 수 있는 문장"이다.
2. **최소 파일 집합**: 매니페스트(package.json·pyproject·Cargo.toml 등) → 진입점 → 테스트 → 설정 → 문서 순으로, 질문에 답할 가장 작은 집합을 고른다. 넓은 검색은 `cofa-explorer`에 위임하되 종합은 리더가 한다.
3. **기준선 실행**: 빌드·테스트·린트 명령을 **실제로 한 번 실행**하고 종료 코드와 요약을 적는다. 변경 전 상태를 모르면 변경 후 실패가 내 탓인지 알 수 없다. 완료 기준: 기준선 결과가 문서에 있다.
4. **직접 경로 읽기**: 질문에 닿는 코드 경로를 입력 → 처리 → 저장/출력 → 실패 처리 순으로 따라간다. 경계는 필요한 만큼만 넘는다.
5. **지도 작성**(`docs/onboard.md`): 진입점, 실행·빌드·테스트 명령, 모듈 그래프(3~7 노드와 화살표), 관례(이름·오류 처리·import·테스트 패턴), 위험 지점(동시성·외부 I/O·보안 경계·삭제/덮어쓰기), 미확인.
6. **라벨**: 모든 주장에 **증거**(코드·테스트·설정이 직접 보여줌) / **추론**(증거에서 끌어낸 결론) / **미확인** 중 하나를 붙인다. "왜" 질문이면 경쟁 설명을 확신도 순으로 표에 정리한다.
7. **중단 조건**: 질문에 답했거나, 남은 불확실성을 줄일 가장 작은 읽기 전용 프로브를 이름 지었으면 멈춘다. 더 찾지 않는다.
8. `$evidence-log`에 엔트리.

## 규칙
- 코드·설정 파일을 수정하지 않는다. `docs/onboard.md`·`docs/decision-log.md` 기록만 예외다. 구현 계획도 여기서 쓰지 않는다(→ `$plan`).
- 증거가 뒷받침하지 않는 권고를 하지 않는다. 추측을 증거처럼 쓰지 않는다.
- 200줄 넘는 파일은 outline 후 필요한 구간만 읽는다.
- 모든 경로는 저장소 루트 기준으로 `파일:줄`.

## 출력 (docs/onboard.md 형식)
```
# onboard — <저장소/질문> — 날짜
## 질문
## 기준선: `명령` → 종료 코드, 요약
## 진입점과 실행 방법
## 모듈 그래프 (A → B: 역할)
## 관례
## 위험 지점
## 랭킹 설명 ("왜" 질문일 때) | 순위 | 설명 | 확신도 | 근거 |
## 증거 (파일:줄) / 추론 / 미확인
## 다음 프로브 또는 다음 행동
```
