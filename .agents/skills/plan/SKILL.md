# plan — 계획

계획은 실행자가 추측 없이 따라 할 수 있을 때 완성된다. 계획 단계에서는 코드를 고치지 않는다.

## 언제 쓰나
- 과제가 2개 이상 파일에 걸치거나 범위가 불명확할 때(Scoped/Complex).
- 사용자가 "계획", "어떻게 나눌지", "범위 정리"를 요청할 때.

## 언제 쓰지 않나
- 파일 1개의 자명한 수정(Trivial). 바로 고치고 `$verify`.
- 사용자가 "그냥 해"라고 했고 범위가 분명할 때 → `$execute`.

## 절차
1. **분류**: Trivial / Scoped / Complex와 이유 한 줄. `docs/decision-log.md`에 첫 엔트리를 쓴다. 완료 기준: 엔트리가 저장돼 있다.
2. **사실 수집**: 관련 파일·테스트·설정을 직접 읽는다. 넓은 탐색이 필요하면 `cofa-explorer` 서브에이전트에 "무엇을 찾을지·어디까지·보고 형식"을 명시해 위임한다. 코드베이스에서 찾을 수 있는 것을 사람에게 묻지 않는다. 완료 기준: 변경 대상 파일 목록과 각 파일의 역할이 적혀 있다.
3. **사람에게 물을 것만 묻는다**: 우선순위, 범위 선택, 위험 허용도. 한 번에 한 질문. 답이 없으면 가장 보수적인 가정을 적고 진행한다.
4. **계획 작성**: Complex이거나 고위험이면 `cofa-planner` 서브에이전트에 위임하고, Scoped면 리더가 직접 쓴다. `templates/plan.md` 형식. 각 단계에 대상·변경·완료 기준·위험. 수용 기준은 "명령 X → 관찰 Y" 형태.
5. **비판(단일 분기)**: Scoped면 선택적으로 `cofa-architect`에 계획 **원문만** 주고 반론 1회를 받아 반영한다(작성자의 결론은 주지 않는다). Complex이거나 고위험(삭제·프로세스 제어·보안·마이그레이션·공개 API)이면 여기서 멈추고 `$design-review`로 넘긴다. 두 경로를 동시에 돌리지 않는다.
6. **저장·승인**: `docs/plans/<slug>.md`로 저장한다. 사용자가 **이미 구현을 요청했고 범위·수용 기준이 명확**하면 "계획 기록, 진행합니다"라고 알리고 `$execute`로 바로 간다(미결 범위·위험이 있으면 그 항목만 한 번 묻는다). 범위가 불명확하거나 고위험이면 "승인 대기"로 표시하고 명시적 승인을 기다린다. 사용자가 계획의 단계·범위·수용 기준을 **바꾸거나 빼면**, 그 항목을 `docs/submission-notes.md` 2절에 "AI 제안 → 사용자 결정 → 바꾼 내용 → 이유" 한 행으로 적는다(`$submission-notes`). 승인만 했으면 적지 않는다.

## 규칙
- 3~6단계. 30개 세부 단계도, 2개 모호한 지시도 아니다.
- 계획의 주장 중 80% 이상이 파일:줄을 인용하고, 수용 기준의 90% 이상이 테스트 가능해야 한다.
- 범위 밖(하지 않을 것)을 반드시 적는다.
- 새 의존성 추가는 계획에 명시하고 사용자 승인을 받는다.

## 출력
- 계획 파일 경로
- 분류·수용 기준·단계·검증 계획·범위 밖·열린 질문 요약
- 다음 행동: "승인하면 `$execute`로 진행"
