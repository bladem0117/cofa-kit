# handoff — 인계 문서

2026-07 코파톤 후기 두 가지가 근거다. "명시적으로 handoff를 남기고 새 세션에서 이어가는 타이밍을 미리 잡아두지 않은 게 실수"였고, Top3에는 "handoff를 만드는 skill"이 있었다. FDE 평가에는 Communication 축(다음 담당자가 인수 가능한가)이 따로 있다.

## 언제 쓰나
- `/status`에서 컨텍스트 사용이 60%를 넘었을 때(그 뒤 `/compact` 또는 `/new`)
- 작업 루프의 단계 전환(계획 승인 직후, 구현 완료 직후, 검증 완료 직후)
- 제출 직전(심사자·다음 담당자용)
- 긴 턴을 `/goal`로 돌리기 전

## 절차
1. **현재 위치**: 과제 한 줄, 분류, 지금 단계(1~7), 마지막으로 끝낸 것, 진행 중인 것. 완료 기준: 처음 보는 사람이 두 줄 안에 어디까지 왔는지 안다.
2. **결정과 이유**: 지금까지의 핵심 결정 3~7개를 "무엇 — 왜 — 대안 — 엔트리 번호"로. `docs/decision-log.md`를 복사하지 말고 포인터로.
3. **검증 상태**: 수용 기준 표를 VERIFIED/PARTIAL/MISSING과 명령으로. 마지막으로 돌린 테스트 명령과 결과.
4. **다음 행동**: 바로 시작할 수 있는 다음 한 단계(명령 또는 스킬 호출). 그다음 두 단계는 한 줄씩.
5. **열린 위험·질문**: 확인 못 한 가정, 사용자 결정이 필요한 것, 알려진 한계.
6. **환경 메모**: 리더 모델·effort, 가용 모델, spawn 가능 여부, 막힌 것(중첩 exec 등). 캘리브레이션 엔트리 포인터.
7. 저장 후 새 세션을 열면 첫 메시지는 "`docs/handoff.md`를 읽고 '다음 행동'부터 이어가라". `$evidence-log` 엔트리 1개.

## 규칙
- 한 화면(약 60줄) 안에. 길어지면 포인터로 바꾼다.
- 결론 먼저, 명령·경로는 그대로 인용.
- 사람이 손으로 고친 부분은 "(직접 수정)"으로 표시해 `docs/submission-notes.md`와 맞춘다.
- 제출용 handoff에는 "다음 담당자가 30분 안에 할 수 있는 것" 절을 추가한다(Communication 축).

## 출력 (`docs/handoff.md`)
```
# handoff — <과제> — <시각>
## 현재 위치
## 결정과 이유 (엔트리 포인터)
## 검증 상태 | 기준 | 상태 | 명령 → 결과 |
## 다음 행동 (1개 + 이후 2개)
## 열린 위험·질문
## 환경 메모
## (제출용) 다음 담당자가 30분 안에 할 수 있는 것
```
