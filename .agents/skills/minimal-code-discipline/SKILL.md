# minimal-code-discipline — 최소 코드 규율

diff를 작고 명백히 올바르게 유지하되, 사용자를 지키는 검사는 절대 줄이지 않는다. 쓰기 전에 적용하는 규율이다. 쓴 뒤 치우는 것이 아니다. 평가자는 "AI의 오버엔지니어링을 조절하는 것은 여전히 인간의 몫"이라 말하고 Cognition 평가의 중심에 둔다(2026-10 팟캐스트).

## 언제 쓰나
- 새 코드를 쓰기 직전(계획 단계 포함)
- 진행 중인 변경이 요청 범위보다 커지고 있을 때
- 사용자가 최소·간결·최단 diff를 요구할 때

## 언제 쓰지 않나
- 사용자가 명시적으로 넓은 기능·미래 대비 구조를 요청했을 때(명시 범위가 우선)
- 사용자가 버릴 것이라고 표시한 탐색용 스캐폴딩

## 사다리 (위에서부터 묻는다)
1. **존재 필요** — 이 변경이 있어야 하는가? 추측된 미래 요구만을 위한 것이면 하지 않는다. **범용 모범사례라는 이유만으로도 넣지 않는다**(평가자 예: 읽기 전용 API 뒤의 DB에 쓰기 가드·트랜잭션 경계를 촘촘히 넣으면 "잘 설계됐지만 우리 요구에 맞춘 것은 아니다"). 완료 기준: "왜 필요한가" 한 줄이 요구사항에 연결된다.
2. **재사용 우선** — 같은 저장소에 헬퍼·타입·패턴이 이미 있는가? 몇 파일 떨어진 헬퍼를 복사하지 않는다. 재사용하거나 한 곳으로 추출한다. 완료 기준: 검색(이름·기능)을 했고 결과를 적었다.
3. **의존성 사다리** — 표준 라이브러리 → 플랫폼 기본 기능 → 이미 설치된 의존성 → 직접 작성. 새 의존성은 몇 줄의 코드로 되면 넣지 않는다. 사용자 승인 없이는 추가하지 않는다.
4. **이해 후 최소화** — 영향받는 코드와 실행 경로를 먼저 읽는다. 문제를 이해한 뒤 가장 짧은 올바른 diff를 낸다. 쓰지 않은 코드는 깨지지 않는다.
5. **지루함 우선** — 영리한 코드보다 명백한 코드.
6. **한계 표시** — 의도적 단순화에는 짧은 주석으로 받아들인 한계와 교체 조건을 적는다.
7. **증상 아닌 원인** — 보고된 증상마다 패치하지 말고, 모든 호출자가 공유하는 원인을 고친다.

## 비협상 (절대 줄이지 않는다)
- 신뢰 경계를 넘는 곳의 입력 검증
- 데이터 손실을 막는 오류 처리
- 보안 통제(인증·권한·비밀값 처리)
- 접근성 기본
- 사용자가 명시적으로 요청한 범위

## 완료 전 확인
- 추가된 모든 줄이 제 몫을 하는가(추측적 일반화·중복 헬퍼 없음)
- 명시된 문제를 올바르게 푸는 가장 짧은 diff인가
- 비협상 항목이 온전한가
- 테스트가 통과하고, 요청 외 동작은 바뀌지 않았는가

## 출력
- 사다리 각 단계에서 내린 결정 한 줄씩(특히 2·3단계의 검색·선택 결과)
- 받아들인 한계와 교체 조건
- AI가 제안했다가 **뺀 과설계**는 `docs/submission-notes.md` 2절에 한 행(제안 · 거부 · 이유=우리 요구). 사람 개입 기록이자 Cognition 답변 재료다
