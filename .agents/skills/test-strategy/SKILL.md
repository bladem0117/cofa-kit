# test-strategy — 테스트 전략과 TDD

OMC `test-engineer`의 계약이다. 테스트는 기대 동작의 실행 가능한 문서다. 구현 뒤에 쓰는 테스트는 설계 효과를 놓치고, 불안정한 테스트는 스위트 전체의 신뢰를 깎는다.

## 언제 쓰나
- 구현 전·중(새 동작 추가, 버그 수정의 회귀 테스트)
- 사용자가 테스트·TDD·커버리지를 요구할 때
- 테스트가 간헐적으로 실패할 때

## 절차
1. **기존 패턴 파악**: 프레임워크, 디렉터리 구조, 명명, setup/teardown, 실행 명령. 그 패턴을 따른다. 완료 기준: 실행 명령을 한 번 돌려 기준선 결과를 적었다.
2. **기준 → 테스트 목록**: 수용 기준마다 테스트를 매핑한다. 정상 경로 1, 경계값(빈 값·0·최대·off-by-one) 1 이상, 오류 경로 1 이상, 순서·동시성이 있으면 1. 테스트 하나는 동작 하나. 이름은 기대 동작을 문장으로("필터에 맞는 사용자가 없으면 빈 배열을 돌려준다").
3. **TDD(새 동작일 때)**: RED — 다음 동작의 테스트를 쓰고 실행해 **실패를 확인**한다(첫 실행에 통과하면 테스트가 틀렸다). GREEN — 통과시킬 최소 코드만. REFACTOR — 테스트를 유지한 채 정리. 반복.
4. **커버리지 공백 표**: 테스트 없는 함수·경로를 위험도(높음/중간/낮음)와 함께 적는다. 전부 메우지 않는다. 높음만 이번 범위.
5. **불안정 테스트**: 원인 분류(타이밍 / 공유 상태 / 환경 / 고정 날짜 / 순서 의존) → 맞는 처방(대기 조건, beforeEach 정리, 상대 날짜, 격리). 재실행으로 운 좋게 통과한 것을 고친 것으로 치지 않는다.
6. **전체 실행**: 변경 후 관련 스위트 전체를 돌리고 신선한 결과를 인용한다.
7. `$evidence-log` 기록.

## 규칙
- 테스트를 통과시키려고 테스트를 약화·삭제·skip하지 않는다. 프로덕션 코드의 원인을 고친다.
- 테스트만 쓴다. 구현 코드가 바뀌어야 하면 `$execute`에 넘긴다(TDD의 GREEN 단계는 예외).
- 거대 테스트 금지. 한 테스트가 여러 동작을 검증하면 나눈다.
- 피라미드는 방향이다(단위 다수 → 통합 소수 → e2e 최소). 비율을 강제하지 않는다.

## 출력
- 기준 ↔ 테스트 매핑 표
- 실행 명령과 결과(통과/실패 수)
- 커버리지 공백 표(위험도)
- 불안정 테스트 진단과 처방
