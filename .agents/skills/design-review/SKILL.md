# design-review — 독립 검토 기반 설계 합의

OMC/OMX의 ralplan(Planner → Architect → Critic) 핵심만 가져왔다. 핵심은 세 가지다. **같은 스냅샷**을 검토하고, 검토자끼리 **서로의 결과를 보지 않으며**, **작성자만 종합**한다.

## 언제 쓰나
- Complex 과제, 또는 고위험 변경(삭제·프로세스 제어·동시성·보안·마이그레이션·공개 API)의 계획
- 선택지가 둘 이상이고 트레이드오프가 분명치 않을 때
- 사용자가 "설계 리뷰", "합의", "계획 검토"를 요청할 때

## 언제 쓰지 않나
- Trivial/Scoped 과제. `$plan`의 5단계(architect 비판 1회)로 충분하다.
- 코드가 이미 작성된 뒤의 결함 리뷰 → `$review`/`$crosscheck`.

## 절차
1. **스냅샷 고정**: 계획 파일(`docs/plans/<slug>.md`, `templates/plan.md` 형식)을 저장하고 버전 번호를 붙인다(v1). 이후 검토는 이 파일만 본다. 완료 기준: 파일 경로와 버전이 기록됐다.
2. **결정 요약 첨부**: 원칙 3~5개, 결정 동인 상위 3개, 실행 가능한 선택지 2개 이상(각각 이점·비용·되돌리기). 선택지가 하나뿐이면 왜 다른 것이 탈락했는지 쓴다. 고위험이면 사전 부검 3가지(어떻게 실패하는가)와 확장 검증 계획(단위·통합·관측).
3. **`cofa-architect-deep` 검토**(읽기 전용, xhigh — 이 스킬에서만 쓴다): 등록된 커스텀 에이전트를 spawn해 스냅샷과 결정 요약만 준다. 요구: 가장 강한 반론, 실제 트레이드오프 긴장 1개 이상, 사전 부검 3가지, 가능하면 종합안, 원칙 위반 지적. 완료를 기다린다.
4. **`cofa-reviewer` 검토**(읽기 전용): 3이 끝난 뒤 **같은 스냅샷**을 별도 spawn으로 준다. `cofa-architect-deep`의 결과는 주지 않는다. 요구: 원칙–선택지 일관성, 대안의 공정성, 위험 완화의 구체성, 수용 기준의 테스트 가능성, 검증 단계의 구체성. 판정 APPROVE / ITERATE / REJECT.
5. **종합**: 두 결과가 모두 돌아온 뒤 작성자(리더 또는 `cofa-planner`)만 두 피드백을 합쳐 v2를 쓴다. 검토자가 계획을 직접 고치지 않는다.
6. **반복**: `cofa-reviewer`가 APPROVE가 아니면 3~5를 반복한다. 최대 3라운드. 라운드마다 `templates/review-round.md` 형식으로 `docs/decision-log.md`에 기록.
7. **종결·재승인**: APPROVE 또는 3라운드 소진. 소진 시 남은 지적을 "알려진 한계"로 명시하고 사용자 결정을 받는다. 최종 계획에 ADR 요약(결정·동인·대안·선택 이유·결과·후속)을 붙인다. 검토로 바뀐 최종본(v2 이상)은 **사용자에게 다시 보여 재승인**을 받은 뒤에만 `$execute`로 넘긴다. 사용자가 모르는 변경이 구현에 들어가면 안 된다. `$plan`과의 역할: `$plan`은 계획 작성, 이 스킬은 Complex·고위험 계획의 검토·합의만.

## 규칙
- 검토자는 순차로, 각각 완료를 기다린 뒤 다음을 띄운다. 병렬로 띄우지 않는다(같은 스냅샷 보장, 교차 오염 방지).
- 사용자가 명시적으로 실행을 승인하기 전에는 소스 수정·커밋·실행 스킬 호출을 하지 않는다. 산출물은 "승인 대기".
- 검토자에게 작성자의 선호나 결론을 주지 않는다.
- 비용 상한: 라운드 3회. 그 안에 합의가 안 되면 문제가 계획이 아니라 요구사항에 있다 → `$plan`의 열린 질문으로 사용자에게 돌린다.

## 출력
- 최종 계획 파일 경로와 버전
- 라운드별 architect·reviewer 핵심 지적과 반영
- 판정과 알려진 한계
- 다음 행동: "승인하면 `$execute`"
